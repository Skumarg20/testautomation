## What the sources say offline and sync are

### Two different products
- **Web app (browser, `isElectron = 0`)**: always online. There is no offline mode, no local store, no write queue and no automatic retry. The service worker caches only the app shell (`assetGroups` app and assets, no `dataGroups` for API calls) (`newmarg-webangular20/ngsw-config.json:1-29`; registered when `production` is true, `web/app.module.ts:191-194`). Every environment the suite targets builds with `isElectron: 0` (`environments/environment.preprod.ts:36`, `environment.qa.ts:13`); only `environment.electron.ts:29` sets `isElectron: 1`.
- **"Offline EXE" (Electron desktop app, `isElectron = 1`)**: a local API and database. Data moves to the cloud through the separate DataSync service (`OfflineOnline/*`, `OfflineOnlineDataSync/*`) (`web/Globals/global.ts:18264-18280`). Jira and support call it "Offline EXE", "MargBooks EXE" or "offline software" (`jira_vectordb.csv#MBC-14570`, `#MBC-16439`, `support_tickets_vectordb.csv#MB-36899`; `jira_vectordb.csv#474fb514`). Internal procedure docs describe it: requirements (7-day trial, licence, encryption, multi-user, re-registration, `onedrive_processed_data.csv#1767bfd4`), limitations compared with the web version (`#12aac924`), setup (`#3931a4e7`), security (`#74ab0bd1`), the desktop licence process (`#49d0d0a8`) and offline user registration with Username, Password and Branch Code (`#b94c9013`).
- The care portal has **no** how-to article on data sync or the offline EXE (re-checked 2026-10-12). The only "offline" articles are about the GST Offline Tool, which is a different feature owned by the GST journey (`careportal_enriched_v5.csv#183522`, `#183524`; `careportal_enriched_v5.csv#783194d4`, `#5b6ce40a`). It does have "How to display Internet Speed" (Control Room > search 'Speed' > 'Show Internet Speed', `careportal_enriched_v5.csv#ec34efb4`) and "How to Speed up Marg Books" (step 1: check internet connectivity, `careportal_enriched_v5.csv#9c1f6e94`). The video transcripts mention internet only in passing ("Your internet is a bit slow", `vimeo_transcripts_hinglish_english.csv#video 3 @746s`, `vimeo_transcripts_hinglish_english.csv#97d3c067`).

### What the web app does when the connection drops
- `ng-connection-service` 1.0.4 listens only to the window `online` and `offline` events (`newmarg-webangular20/node_modules/ng-connection-service/fesm2015/ng-connection-service.js:11-14`). Playwright `context.set_offline(True)` fires these events and sets `navigator.onLine = false`, so the code paths below can be reached from a browser.
- **Full-screen overlay** at the root component: "No internet connection found." / "Check your connection or try again.", `position-fixed`, `z-index: 500000000` (`web/app.component.ts:29-35`). It is driven by `monitor()` plus an initial `navigator.onLine` check (`web/app.component.ts:141-158`) and is enabled only when `isElectron == 0 && isAzure == 1` (`web/app.component.ts:108`); preprod has `isAzure: 1` (`environments/environment.preprod.ts:2`).
- **Header icon**: a no-wifi icon is shown while `noInternetConnection` is true (`web/Layout/homeLayout.component.html:487-498`). The speed widget is hidden at the same time (`homeLayout.component.html:509`). The layout tracks the state from `monitor()` (`web/Layout/homelayout.component.ts:408-423`).
- **Slow-internet banner**: "Slow internet connection. Please check your internet setting" when the class is `red` (`homeLayout.component.html:1-10`). The class is set every 5 s from `navigator.connection.downlink`: below 2 Mb/s is red, 2 to 6 yellow, above 6 light green. This runs only when `isElectron == 0` and the profiler flag `InternetSpeed == "T"` (`homelayout.component.ts:771-786`, `:1096`). The care portal names the setting: Control Room > 'Show Internet Speed' (`careportal_enriched_v5.csv#ec34efb4`), and an internal doc screenshot shows the red banner with this exact text (`onedrive_processed_data.csv#1950b4c6`).
- **Failed API call (status 0)**: `MrgHttpService.httpConnection` catches "Http failure response ... 0 Unknown Error" and, on the web (`isOnlineOffline == 0`, preprod `environment.preprod.ts:38`), **navigates to `/error`** (`web/Services/MrgHttpService.service.ts:467-479`). `/error` is a public route (`web/app-routing.module.ts:183`) that shows "Website Under Maintenance" / "We're Sorry! Web site is down for maintenance / Please try after some time" (`web/Component/errorpage.component.ts:17-20`). When it loads, it calls a user-detail API; on success it **clears localStorage and goes to `/login`** (`errorpage.component.ts:57-65`). So the web "recovers" from a dropped save by logging the user out. There is no retry.
- **Per-feature guards** use `AlertMsg.NoInternent` = "Internet Required for this option!" (`web/Globals/global.ts:19031`). They cover: sale list Email, Upload Bills and WhatsApp (`web/Component/Transaction/InverntoryTransaction/processout.list.component.ts:1308-1336`), WhatsApp send (`web/Services/Common.service.ts:4399-4400`, `:4990-4991`), the help-portal links and the Pharma helpline in the header (`homelayout.component.ts:2682-2684`, `:2785-2787`), the support ticket (`web/Layout/support-ticket.component.ts:363`, `:416`, `:675`), bank payment (`web/Component/Transaction/Voucher/bank.payment.component.ts:438`, `:502`), and the Data Sync request buttons (`web/DataSync/data-syncreport.component.ts:224`, `:256`). No guard covers the sale-bill save itself: `processout.transaction.component.ts:830-844` sets `noInternetConnection` but the save path never reads it.

### Data sync as seen from the web
- Route `/other/datasyncreport` → `DataSyncReportComponent` (`web/Modules/other.home.module.ts:54`; `other` is lazy-loaded under the guarded layout, `web/app-routing.module.ts:122`). The menu row "DataSync Details" under "Other Tools" has `isactive: 0` (`api/margerpdata/DatabaseJson/menumaster.json:5911-5917`; `api/margerpdata/Database/AlterMainDB.xml:1319`), so on the web the screen can be reached only by direct URL.
- On the web the screen shows: heading "Data Sync", "Currently logged in with the following Email: <email>", "Report Date: dd-MM-yyyy", a status message and the **Enable Data Sync** / **Cancel** buttons (`web/DataSync/data-sync.Reportcomponent.html:8`, `:34-36`, `:126-131`, `:135-139`). The grid, Add, Refresh and Upload are Electron-only (`:11-25`, `:146-149`). "Last Sync" is commented out (`:140-142`).
- Status texts: 0 "Your request is pending for approval", 1 "Your request has been approved!", 2 "Your data sync request is cancelled by Admin..." (`data-syncreport.component.ts:210-216`). With no request row the API returns 201 and the UI shows no text plus Enable Data Sync (`:217`; `api/margerpdal/OfflineOnlineDataSync.cs:2167-2171`).
- Enable inserts a row in `tbldataSyncRequest` keyed by complinkid and dbinfolinkid (`OfflineOnlineDataSync.cs:2112-2127`; `codekb:MargBooks:api#127ceb23` SyncRequestsave, `#89e8b37a` SyncRequeststatus). The alert on success is "Request has been accepted!", otherwise "Request not sent!" (`data-syncreport.component.ts:248-251`). Cancel asks "You Won't be able to send request again. Are you sure want to cancel ?" (`:189`). After a cancel (status 2), a new request gets 401 "Invalid request" (`OfflineOnlineDataSync.cs:2108-2113`). Sending the same status twice returns 200 "Already requested" (`:2090-2095`).
- **Transaction lock**: on web login the layout reads the request status. If it is approved (1), `DatasyncSetting.isDataSyncEnable = true` (`homelayout.component.ts:3457-3474`), and opening `/transaction` from the menu, or F10/F3/Del/C on a bill, then shows "Transaction locked after datasync" (`global.ts:19714`; `homelayout.component.ts:3088-3096`; `processout.transaction.component.ts:15094-15095`; `voucher.list.component.ts:705-706`; `physicalstock.transaction.component.ts:1060-1061`; `transactionin.list.component.ts:1142`). Support ticket: "TRANSACTION LOCKED AFTER DATA SYNC" (`support_tickets_vectordb.csv#MB-17130`; no chunk found). A KB-only Jira task asks to "restore offline data in web credentials and enable billing on web" (`jira_vectordb.csv#c3522d92`), which suggests the lock is lifted by a restore step.
- `/datasync` ("Online Data Sync From Server": E-mail, Password, Branch Code, Submit) is a public route (`app-routing.module.ts:191`), but on the web its whole body is `[hidden]="!isElectron"` (`web/DataSync/data-sync.component.html:2-3`, `:84`).
- The dashboard "Last Sync : date | time" is the dashboard cache refresh, not data sync (`web/Layout/dashboard.component.html:77`). It belongs to J22 (`scenarios/dashboard.md` DB-06; care portal "How to Sync and Refresh Dashboard", `careportal_enriched_v5.csv#5888d6dd`, `#3bf80b35`). Users mix the two up ("HOW TO SYNC S REFRESH dashboard", `support_tickets_vectordb.csv#MB-32483`; "Dashboard time is showing wrong even after sync", `#MB-19851`; "sync time mismatch always", `#MB-20097`).

### Electron-only sync engine (API side)
- `GET OfflineOnlineDataSync/pushpull?type=` with 1 = upload local → server and fetch status, 2 = HO download, 3 = both (comment at `api/MargApp.DataSyncSvc.Api/Controllers/OfflineOnlineDataSyncController.cs:31`; `codekb:MargBooks:api#25fd85b5`, second service `#b33fc71b`). The Electron Upload menu calls type 3 (`data-syncreport.component.ts:178-185`) and then every 300000 ms posts `UploadDataLocalToServerjob` (`:126-133`; `codekb:MargBooks:api#70a700ce`, `#ba2131af`).
- `GET getSyncDataFromLocal` feeds the grid: Particulars Name, Total Records, Success, Failed, Pending (`data-syncreport.component.ts:96-102`, `OfflineOnlineDataSyncController.cs:171-187`).
- `POST OfflineOnline/UservalidateforO2DM` (E-mail, password, branch code). A blank branch code returns "Invalid branchcode" (`api/MargApp.DataSyncSvc.Api/Controllers/OfflineOnlineController.cs:36-56`). After the OTP step the UI shows "Data sync Completed" and goes to `/login` (`web/DataSync/data-sync.component.ts:197-243`).
- HO/branch: `syncsetting` requires `branchlinkid` (`OfflineOnlineController.cs:234-244`). `SetGetdatasyncsetting` caches the setting in memory for the current day (`api/margerpdal/OfflineOnlineDataSync.cs:1691-1717`).
- The Electron internet check opens a fixed production URL (`api/margerputil/UtilFunction.cs:2547-2560`, exposed as `Util/IsInetrnetavailable`, `api/margerpapi/Controllers/UtilController.cs:945`; `codekb:MargBooks:api#6c901745`, Electron variant `#3e29e82a`).
- Electron licence grace: each offline day increments `LicenseCheckFlag`. Above 15 days the app shows "Please Connect To internet" and logs out (`web/Login/login.component.ts:1553-1561`, `:1571-1575`). When the local server is unreachable it shows "Software is not connected with server, May be your server system is switched off or API is stopped." (`web/Services/MrgHttpService.service.ts:990-999`).

## KB vs live app (not resolved; a human decides)
1. **KB re-run (2026-10-12).** KB chunk citations were backfilled via `search_kb`. Keys with no chunk next to them (for example MB-36422, MB-35483, MB-19580, MB-17130, MB-7335, the slow-internet false-positive tickets and MST-035) had no matching chunk; they rest on the local CSV rows only.
2. **No care-portal article on data sync or the offline EXE.** Still true after the re-run; the only "offline" care articles are about the GST Offline Tool (`careportal_enriched_v5.csv#783194d4`, `#5b6ce40a`). The KB does hold internal procedure docs for the offline EXE (`onedrive_processed_data.csv#1767bfd4`, `#12aac924`, `#49d0d0a8`, `#b94c9013`), but none describes the web Data Sync request strip or the transaction lock. The user-facing expected behaviour still comes from code and tickets.
3. **Overlay vs per-feature guards.** On preprod (`isAzure 1`) the root overlay covers the whole screen when offline, so the many "Internet Required for this option!" guards (DS-09, DS-10, DS-17) cannot be reached with the mouse. Either the guards are dead on the web or the overlay is not shown in some builds. Live check needed.
4. **Offline save leads to "maintenance" and logout.** A dropped request takes the user to "Website Under Maintenance" and, after reconnecting, clears the session (DS-05/06/24). The message is misleading, which matches ticket MB-7335 ("page goes into maintenance ... not internet"). Decide whether this is the intended web behaviour or a defect to report before asserting it.
5. **`pushpull?type=3`** does not run the HO download branch (DS-35; handler cards `codekb:MargBooks:api#25fd85b5`, `#b33fc71b`), although the comment and the Electron Upload call expect "1 and 2". This may explain sync complaints (MBC-14570, MB-36899). Needs a developer to confirm.
6. **Status 2 wording.** It always says "cancelled by Admin", including when the user cancelled it themselves (`data-syncreport.component.ts:187-198` vs `:215`).
7. **Status checks use different ids.** The layout uses `UserLoginData.uloginDetailData.DBInfolinkid` (`homelayout.component.ts:3461`); the Data Sync screen uses `UserLoginData.userData.DBInfolinkid` (`data-syncreport.component.ts:204`). If these differ, the lock and the screen can disagree.
8. **Upload interval leak (Electron).** Each Upload click starts another 300 s `setInterval` and never clears it (`data-syncreport.component.ts:127-133`).
9. **`isApprovalWindow` and `isSyncApproved`** are forced true in `ngOnInit` (`data-syncreport.component.ts:56-57`) regardless of the `SetGetdatasyncsetting` result, so the web strip always renders.
10. **Production host in the Electron internet check** (`UtilFunction.cs:2547-2560`). Any Electron test would reach a production host, which conflicts with rule 4 (production is never a test target).
11. **The journey name says "(Electron app)"** but the matrix layer is `manual`. Most of the real sync behaviour (DS-30 to DS-47) is not reachable from Playwright against the web; the web part is the connection-loss handling and the Data Sync request strip. Suggest splitting J35 into a web connection-loss journey and an Electron/API journey.
12. **Shared-account risk.** DS-18 and DS-19 permanently change `tbldataSyncRequest` for the company (cancel cannot be undone), and an approved request locks transactions for every test on that company (DS-20). Run them only on a dedicated throwaway company.
13. **EXE sign-up without internet: defect or design?** The Desktop Licence Process doc says "Internet is mandatory during Sign up in the Desktop exe" (`onedrive_processed_data.csv#49d0d0a8`), while MB-35318 / MBC-14328 treat "Internet Required for this option!" at EXE sign-up as a defect and a fix was retested (`jira_vectordb.csv#d5402625`, `#3e4e44f1`). DS-42's expected value is unchanged; a human decides which rule is current (DS-49 assumes the doc).
14. **Transaction lock release.** The KB has a task "restore offline data in web credentials and enable billing on web" (`jira_vectordb.csv#c3522d92`), which implies billing on the web is re-enabled after a restore. No code path for lifting the lock was found for DS-20; check with a developer.
