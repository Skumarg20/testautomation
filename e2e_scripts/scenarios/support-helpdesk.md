## Safety classes (read first)
Saving a ticket is not a local write. `POST MargSupport/Save` forwards the form as multipart `Jsondata` (plus an optional `image` part) to `{NewMargSupportUrl}/MBSupport/SaveProblem`, which is Marg's live support desk (`margerpapi/Controllers/MargSupportController.cs:229-239`). When that returns `success` and the ID is `"0"`, the API also:
- queues a WhatsApp message to `91<Mobile>` with template `9205555~<user>~<TicketNo>~<dd/MM/yyyy>` (`:261-277`);
- emails the template with `moduletype 14` to `Emailid` (`:283-288`).

Delete (`MargSupport/MBSupportDeleteRecord`) and reopen/chat (`MargSupport/MBSupportUpdateStatus`) also write to the live desk (`src/app/Globals/global.ts:252-256`).

- **(a) safe UI-only.** It opens screens and reads data: `GET MargSupport/MargSupportStaticData`, `POST MargSupport/MargPrtnerSupprtDetail` (a POST, but a read), `GET QuestionSearchMargBook/GetQuestionSugestion`. It also covers validation that blocks before any write, and cancel/close.
- **(b) needs a stub.** Intercept `**/MargSupport/Save` (or `**/MBSupportDeleteRecord`, `**/MBSupportUpdateStatus`) with Playwright `page.route`, assert on the request body, and fulfil it with a canned response. Without the stub this row creates or changes a real ticket. **Never let it pass through.**
- **(c) manual only.** These rows need a real phone/WhatsApp, a third-party widget, or an external site.

## Known defects and complaints
The 2026-10-12 KB re-run found **no Jira issue or support ticket about the support-ticket screen itself**. Support tickets only show general complaints that raised tickets stay unresolved or that their status is unclear (`support_tickets_vectordb.csv#d8dea887`, `#8d857bdf`), and that support is not available round the clock (`support_tickets_vectordb.csv#bdb5db31`). The items below are code-reading findings (candidates, not confirmed defects):
- **D1. F10 on a new ticket throws.** `browserShortCut` reads `this.data.editdata.TicketNo.length`, but Create/F2 opens the modal with `editdata: undefined` (`create-ticket.component.ts:688`, `support-ticket.component.ts:697-700`). F10 in Create mode is therefore a TypeError and nothing is saved. The Save button path is unaffected.
- **D2. Suggestion highlight throws on regex characters.** `highlightMatch` builds `new RegExp(words.join('|'))` from raw user text (`create-ticket.component.ts:331-337`). The special-character filter is commented out in the modal (`:299-303`), although it is active in the old list form (`support-ticket.component.ts:266-271`). So a description such as `GST (sale` or `rate*` gives an invalid regex while the popover renders.
- **D3. No visible error for an empty Description.** Its validation-message binds `ticketForm.get('description')` in lower case, which is a null control (`create-ticket.component.html:110`). The field also has no `*`. Save stops silently at the `IsValidForm` / `Description == ''` guards (`ts:403-409`).
- **D4. Hidden required fields can block Save silently.** `ProductName` defaults to `''` when there is no `selectedPlanDetails`, and it is `Validators.required` (`create-ticket.component.ts:367`). `Mobile` is required from the profile (`:360`). Neither has an on-screen control, so a user with no plan details or no mobile cannot save, and sees no message.
- **D5. Validation labels do not match the field labels.** The fields are labelled "Main Disposition", "Sub Disposition" and "Problem Type", but the popover text is "**Problem Type 1 required !**", "**Problem Type 2 required !**", "**Problem Type 3 required !**" (`create-ticket.component.html:25`, `:46`, `:66`; template `src/app/UtililityComponent/Validation/validation.component.html` "{{label}} required !").
- **D6. Attachment check contradicts its message.** Only `.mbk` is rejected, yet the message says "Invalid image format. Only jpg/jpeg/png format is supported." (`create-ticket.component.ts:715-717`, `global.ts:18966`). Any other type (pdf, exe, zip) is accepted (`accept=""`, `html:163`).
- **D7. Status strings disagree.** Reopen appears for `'Closed'` (`ticket-template-button.ts:55`), while Bitrix edit rules check `'Close'` and `'User Canceled'` (`support-ticket.component.ts:173`).
- **D8. The list search filters on the wrong field.** Search uses the `Problemtype` field (`support-ticket.component.ts:43`, `:513-516`), but the visible column is `SubProblemTypeMargDescriptin` (`:151`). Searching for a visible problem-type text may return nothing.
- **D9. Two licence sources.** The list sends `LicNo` from `userData.licenceno` (`support-ticket.component.ts:423`), while Save sends `superadmindata.licenceno` (`create-ticket.component.ts:365`). On the Bitrix path the server filters the list by LicNo (`MargSupportController.cs:330`), so a ticket can be saved under one licence and listed under another.
- **D10. Empty list shows an error on the Bitrix path.** With `bitrixTicket==1`, an empty ticket list calls `showError(res)` (`support-ticket.component.ts:435-440`). Today the client is set to 0, so this is latent.
